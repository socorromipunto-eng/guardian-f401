## Root cause and classification

The installer pinned Windows CRLF bytes, while the committed Git blob uses LF.
LF: 731 bytes, SHA-256 67FE8ED47D02BD26C81319A22A28917704B0FFE755EF8A60FB4109B47348CAAF.
CRLF: 749 bytes, SHA-256 3B6059C6EE7AF006C2F7FFB4B47BD754530BF28A74EF4B89DC65962AAC35931E.
Git blob: f14bd0ca181dd1352974b2c6b8891cbbd734cb5d.
This is an installer integrity-contract portability defect and a prepublication
validation coverage gap. Prior Windows tests did not establish the committed Linux
byte contract. It is not evidence of a firmware defect.

## Decision and exact correction

Pin the canonical reviewed LF SHA-256. Accept only that exact LF content or its
uniform CRLF representation. Reject bare CR, mixed endings, CRCRLF, BOM, truncation,
appended content, changed versions and changed wheel hashes. Do not strip whitespace,
parse/reformat requirements, or accept arbitrary normalized text.
Return the verified LF bytes and write a fresh requirements.lock inside the existing
disposable installation directory. Pass that exact snapshot to pip, avoiding a second
read of the original source after verification. Preserve package versions, URLs,
wheel hashes, download restrictions and offline --require-hashes installation.
No change to governance/requirements.lock, workflow triggers, firmware or keys.

Exact worktree scope: replace tools/install_governance_dependencies.py; create
 tests/governance_tooling/test_aud002_lock_integrity.py and this incident record.
The existing unittest discovery command automatically discovers the new test module.
